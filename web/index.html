ABOUT THIS SPACE

How AllMemory works

A short map of what you are looking at, and the guarantees behind it.

One tenant, one space

Every request resolves to a (tenant_id, agent_id) identity. Queries are always scoped to the tenant, so other spaces are never visible from here.

One account, full control

A single administrator credential opens every workspace: reading, deleting memories and managing agent tokens. The session lives in an HttpOnly cookie, so a refresh keeps you signed in; JavaScript never sees the token.

Two interfaces

Agents use the REST API or the MCP server (Streamable HTTP and stdio). This browser is a third, human-facing window onto the same database.

Portable storage

SQLite is the default for a single host. Point DATABASE_URL at PostgreSQL to enable Alembic migrations and optional pgvector semantic search.

Three memory layers · read the summary first

Every Agent keeps exactly ONE summary: a long Markdown overview of ALL its memories. Other Agents read it first to understand what that Agent is doing, then fetch details only as needed.

  1. summary — the one, potentially long, whole-memory overview per Agent. Writing replaces it and never creates a second one. Highest read priority.
  2. event — the current state of a long-running subject keyed by (category, event_key), e.g. development / finance / health. Versioned.
  3. timeline — an append-only dated log entry with occurred_at, answering what happened and when.

Agents can call memory_guide for the full contract, memory_agents for everyone's summary at once, and memory_context(detail_level="summary") for the overview plus ready-to-use follow-up calls.

Memories keep their source agent, version and timestamps. Console deletions are soft deletes with an audit entry; resolving a thread never rewrites a memory.
